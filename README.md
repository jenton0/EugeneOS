# EUGENE OS

64-бітна операційна система для x86-64, написана з нуля на асемблері та C.
Завантажується через UEFI, працює з FAT32, має графічну оболонку, власний
мережевий стек і — головне — **збирає сама себе**: порт flat assembler
працює всередині системи й асемблює її власне ядро.

```
EUGENE OS  Version 2.0
(C) 2026 Eugene.  All rights reserved.

Type HELP for a list of commands.

C:\>_
```

## Можливості

**Ядро**
- Long mode (x86-64), завантаження через UEFI (OVMF)
- Графічний режим через GOP, розмір екрана визначається динамічно
- Повна таблиця обробників винятків (вектори 0–31) із діагностикою збоїв
- Таймер на IRQ0 (1000 Гц), планувальник на вісім слотів задач
- Власні сторінкові таблиці: тотожне відображення 0…4 ГБ, некешоване MMIO
- Розподільник фізичних кадрів, підкачка сторінок на вимогу
- Власний адресний простір на кожну задачу, повне повернення пам'яті при виході
- Нульова сторінка й сторінка-вартовий під стеком недоступні
- Клавіатура та миша PS/2 (полінг), колесо прокрутки в режимі IntelliMouse

**Файлова система**
- FAT32: читання й запис, робота з підкаталогами
- Коректне поводження з ланцюгами кластерів, підтримка всіх копій FAT
- Файлові дескриптори: `open` / `read` / `write` / `lseek` / `close`

**Текстовий інтерфейс ядра**
- Консоль у стилі MS-DOS із блимаючим курсором
- Вбудований текстовий редактор із прокруткою (буфер 4 МБ)
- Окреме вікно перегляду файлів (тільки читання)

**Графічна оболонка у стилі Windows 3.1**
- Власна віконна бібліотека `libgui`: вікно — це об'єкт із процедурою
  повідомлень, як `WndProc` у Windows
- Перетягування, зміна розміру за всі краї й кути, згортання в піктограму
  на робочому столі, розгортання, системне меню
- Обрізання малювання по межах вікна, справжній порядок вікон
- Елементи керування: кнопки, прапорці, перемикачі, написи, рамки груп,
  однорядкові й багаторядкові поля вводу, списки, смуги прокрутки
- Фокус, обхід по `Tab`, кнопка за замовчуванням на `Enter`
- Меню: рядок меню, спадні списки, підменю, гарячі клавіші `Alt`+літера
- Модальні діалоги, `MessageBox`, вибір файлу, рядок вводу
- Буфер обміну, виділення тексту мишею й клавіатурою, `Ctrl+C/X/V/A`
- Часткове оновлення екрана: перемальовуються лише змінені ділянки
- Растрові зображення BMP, піктограми програм із файлів
- Додатки: диспетчер програм, консоль, блокнот, файловий менеджер,
  переглядач зображень, список задач

**Мережа**
- Перелічення шини PCI
- Драйвер RTL8139 (DMA, кільцевий буфер прийому)
- ARP — запити й відповіді
- IPv4, ICMP — пінг в обидва боки
- UDP, клієнт DHCP, резолвер DNS

**Розробка всередині системи**
- Порт flat assembler 1.73
- Система асемблює власне ядро: `RUN FASM.BIN KERNEL.ASM KERNEL.BIN`

## Збірка

### Що потрібно

| Інструмент | Шлях за замовчуванням |
|---|---|
| flat assembler | `C:\fasm\fasm.exe` |
| MinGW-w64 (gcc, ld, objcopy) | `C:\mingw64\bin\` |
| QEMU | `.\qemu\` |
| Віртуальний диск VHD | `C:\store\1.vhd`, буква `E:` |

Шляхи задаються змінними на початку `build.bat`.

### Запуск

```
build.bat
```

Скрипт монтує VHD, збирає завантажувач і ядро через FASM, компілює
userland через GCC, лінкує плоский бінарник, відмонтовує диск і запускає QEMU.

### Прапорці компіляції — не змінювати

```
-ffreestanding -fno-pie -m64 -mno-red-zone -mgeneral-regs-only
-mno-stack-arg-probe -fno-stack-protector -fno-exceptions
-fno-asynchronous-unwind-tables -fno-ident -O2
```

Кожен має причину:

- **`-mgeneral-regs-only`** — забороняє SSE. Без нього GCC на `-O2` генерує
  `movaps` по стеку, а планувальник ядра не зберігає стан XMM при
  перемиканні задач.
- **`-mno-red-zone`** — обробники переривань пишуть нижче `RSP`.
- **`-mno-stack-arg-probe`** — інакше MinGW вставляє виклики `___chkstk_ms`,
  якої в нас немає.
- **`-fno-stack-protector`** — інакше GCC кличе `__stack_chk_fail`.

### Особливість лінковки

MinGW-ний `ld` працює в емуляції `i386pep` і виконує PE-специфічні дії над
вихідним файлом **завжди**. Тому спроба зробити не-PE вивід (`--oformat binary`
або `OUTPUT_FORMAT(elf...)`) дає:

```
cannot perform PE operations on non PE output file
```

Схема така: `ld` робить звичайний PE, а `objcopy -O binary` зрізає заголовки.
Щоб заголовки не заважали, `linker.ld` збирає **весь образ в одну секцію**
`.image` — тоді `objcopy` кладе її на зміщення 0 незалежно від того, що PE
записав у ImageBase та RVA.

## Команди системи

### Файли

| Команда | Дія |
|---|---|
| `LS` | список файлів із розмірами |
| `CD <dir>` | змінити каталог |
| `BACK` | на рівень вище |
| `MKDIR <dir>` | створити каталог |
| `CREATE <file>` | створити файл |
| `RM <file>` | видалити файл |
| `OPEN <file>` | переглянути файл (тільки читання) |
| `EDIT <file>` | редагувати файл |
| `RUN <app> [args]` | запустити програму |
| `FILE <file>` | який тип у файлу, не відкриваючи його |
| `REN <old> <new>` | перейменувати файл або каталог |


#### Тип файлу визначається за вмістом

Розгалуження за розширенням давало дві тихі вади одразу: `.BIN` і `.APP`
— розширення **програм** — віддавались програвачу відео, а картинку
можна було спробувати виконати. Ім'я файлу не є його типом.

Тому власні формати починаються з підпису `EUGN`, і саме він вирішує,
що робити. Заголовок 16 байтів: підпис, тип, версія, ширина, висота,
прапорці, розмір даних.

| Розширення | Що це |
|---|---|
| `.EUG` | системний файл; без підпису — повідомлення про пошкодження |
| `.EVD` | відео; працює і без заголовка, як старі записи |
| `.BMP` | зображення; лишається як є, на ньому тримаються піктограми |
| `.BIN` `.APP` | програма, і тільки програма |

Розширення лишається **другим** кроком і застосовується лише до чужих
форматів. Команда `FILE` показує, що система думає про файл, не
відкриваючи його.

Оболонка тип не вгадує: диспетчер програм питає ядро (`syscall 36`) і
малює значок за відповіддю. Доти він тримав власну таблицю з п'яти
розширень, і підпис `EUGN` у графічному режимі не означав нічого — а
разом із тим із сітки зникали каталоги, `.EVD`, `.WAD` і файли без
розширення. Тепер видно все, що лежить на диску: незнайомий тип
отримує загальний значок, а не зникає. Ціна — читання одного сектора
на файл під час перегляду каталогу; сам файл не завантажується, тому
22-мегабайтне відео коштує рівно стільки ж, скільки текстовий файл.

#### Каталог із розміром і датою

Номер 27 віддає самі імена одним рядком, і поки список лишався
списком, цього вистачало. Колонок «розмір» і «змінено» з нього не
зробити: тих чисел у рядку просто немає, а дописати їх у 27 не можна —
його формат чекають готові бінарники на диску. Тому `syscall 38`:
каталог приходить записами по 32 байти — ім'я, атрибути, дата й час
зміни, розмір, перший кластер.

Дату беремо з полів **зміни** (`0x18`/`0x16`), а не створення: файловий
менеджер показує «коли востаннє чіпали».

Тут-таки виявилося, що ставити дату не було кому: створюючи запис,
ядро обнуляло всі 32 байти й писало лише ім'я та атрибут. Колонка
«змінено» показувала б `-` для всього, що система зробила сама.
Тепер `FatNow` читає годинник CMOS і штампує запис — і файл, і
каталог. Дата створення при перезаписі зберігається: новий вміст не
робить файл створеним заново.

Шрифт у нас пропорційний, тому колонки пробілами не вирівняти. Список
навчився табуляторів: рядок ділиться символом `\t`, а зсуви задаються в
пікселях — рівно так, як це робили списки з `LBS_USETABSTOPS`. Від'ємний
зсув притискає сегмент правим краєм, і саме ним вирівняно стовпчик
розміру, щоб одиниці стояли під одиницями.

#### Відео на весь екран

Кадр у файлі 320×240, і більше деталей у ньому немає — тому «на весь
екран» означає збільшення, а не різкішу картинку. Множник цілий:
скільки разів ширина й висота кадру вміщаються в екран, менше з двох.
Дробовий давав би рвані краї, бо частина вихідних пікселів займала б
три екранних, частина чотири.

Горизонтальне розтягнення робиться один раз на вихідний рядок, а
вертикальне — копіюванням готового рядка. Розміри кадру беруться із
заголовка, якщо він є; файли без підпису лишаються 320×240.

#### Відео у вікні

Той програвач малює прямо в буфер кадру й сам крутить цикл, тому у
вікні його не показати. Роботу розділено: `syscall 39` відкриває
файл, `syscall 40` розкодовує черговий кадр **у буфер програми**.
Формат лишився там, де й жив — у ядрі; куди й у якому масштабі
покласти готовий кадр, вирішує той, хто має вікно.

Кадр приходить як 32 біти на піксель зверху вниз — рівно те, що
лежить у `GuiBitmap`, тож масштабує його звичайний `gui_bitmap_fit`.
Тут множник уже дробовий: вікно можна тягнути за край, і тримати
цілий множник означало б стрибати розміром.

Такт показу окремий від `GUI_EV_TICK`. Той ходить раз на чверть
секунди, бо його період обрано під миготіння каретки. Відео просить
свій — `gui_frame_events(41)`, ті самі 41 мс, що й у консолі, — і
вимикає його, дограв. Поки ніхто не просить, черга подій така сама,
як була.

Файл при цьому лягає **не** у `VideoMemoryBase`. Той буфер спільний:
у нього читає все — від `bmp_load` до запуску програми. Програвачу
консолі це байдуже, бо поки він грає, більше нічого не відбувається.
У вікні ж достатньо було б відкрити картинку, щоб потік відео посеред
показу перетворився на сміття. Тому окрема ділянка `0xC000000` — між
буферами дескрипторів і купою програм.

Стан декодера в ядрі один, тому й вікно програвача одне: відкрити
друге відео означає перезапустити його з новим файлом. Пробіл —
пауза.

#### Програма у вікні

Той самий прийом, але для чужого коду. Досі запуск програми означав,
що вона забирає екран: `.blit` писав прямо у фреймбуфер, іншого місця
не існувало, а `syscall 37` присипляв того, хто запустив.

Тепер задачі можна видати **полотно** — буфер, куди піде весь її
`blit` замість фреймбуфера. `syscall 41` запускає програму з полотном
і, на відміну від 37, батька не присипляє: поки гра малює в буфер,
оболонка мусить малювати вікно, а спляча задача не малює нічого.

Гру для цього не перезбирали. DOOM і далі кличе ті самі `syscall 9`
і `15` — просто ядро тепер відповідає на них розміром полотна, а не
розміром екрана. Інакше гра розрахувала б кадр під справжній екран, і
у вікно він не влазив би.

Черга клавіатури одна на всіх, і `syscall 1` та `26` тягнуть з неї
обидва. Поки жила одна задача, питання не стояло; тепер оболонка й
гра живі одночасно й крали б клавіші одна в одної через одну. Тому
`syscall 43`: клавіші дістаються дитині, поки її вікно активне. Миша
при цьому лишається в оболонки **завжди** — саме тому клацання по
іншому вікну може повернути клавіатуру, не вбиваючи гру.

Полотно видається в `SpawnAppTask` кожній задачі без винятку: для
звичайного запуску воно нульове, тобто програма малює прямо в екран,
як завжди. Так наступна задача не успадкує полотно попередньої.

Полотно роблять розміром **з екран**, а не в розмір вікна. Спершу воно
було 640x400 — і гра малювала зі зсувом: DOOM центрує кадр під той
розмір, який вважає екраном, і все, що не влізло, зрізалось правим та
нижнім краєм полотна. З полотном на весь екран програма малює точно
так само, як малювала б на весь екран, а вікно вже масштабує готове.

Звідси й друга правка: `gui_bitmap_fit` рахував вихідний стовпчик
діленням на кожен піксель. Поки ним масштабували значки 32x30, це
нічого не важило; на полотні в розмір екрана те саме ділення стало
коштувати сотні тисяч операцій на кадр, тому стовпчики тепер
рахуються один раз на виклик.

#### Спільні буфери й чому їх вистачило

Увесь шар FAT ходить через спільні буфери: `SectorBuffer` (три
десятки місць), `FatCacheBuf`, `DirBuffer`, `SysNameA`, а ще
`DirEntrySector` з `DirEntryOffset` і `VideoMemoryBase` як проміжний.
Поки жила одна задача, питання не існувало. З появою програми у вікні
здавалося, що потрібен повноцінний замок.

Виявилося, що ні — і причина в одному рядку налаштування переривань:

```
mov word [rbx + 4], 0x8E00
```

Вектор `0x80` зареєстровано як **interrupt gate**, а не trap gate.
Такий шлюз скидає прапорець переривань, тобто системний виклик
виконується **до кінця й без витіснення**. Два виклики переплестися не
можуть у принципі.

Небезпечне лишалося одне місце — читання образу програми в `.ra_load`.
Воно йде в задачі ядра з увімкненими перериваннями, і таймер може
спинити його просто посеред обходу ланцюга кластерів. Оновити список
файлів у цю мить означало б переплести дві операції в тих самих 512
байтах — причому зіпсувався б вміст файлу, а не впав стек, тобто
дізналися б ми про це набагато пізніше й зовсім не там.

Тому замість замка — прапорець `FsBusy` на час завантаження і
очікування в диспетчері для тих вісімнадцяти номерів, що працюють із
диском. Перелік номерів лежить одним масивом поруч із перевіркою: одне
місце легше тримати повним, ніж вісімнадцять викликів по тілах.

#### Куди подівся час

Перший робочий запуск дав кадрів десять. Час забирали три речі, і
жодна з них не була самою грою.

**Дві задачі з трьох нічого не робили.** Планувальник ділить час
порівну між *готовими* задачами, а готових було три: ядро, оболонка
й гра. Задача ядра при цьому лише опитувала три прапорці в циклі, а
оболонка крутила `wm_pump()` навіть тоді, коли подій не було. Тобто
грі діставалася третина. Тепер обидві сплять: ядро робить `hlt` у
циклі очікування, а оболонка кличе `syscall 45`, коли за оберт не
сталося нічого. Таймер на 1000 Гц будить обох через мілісекунду —
для опитування прапорців цього з головою.

**Під вікном малювалося те, чого не видно.** `paint_pass` малював
робочий стіл на весь брудний прямокутник, потім усі вікна знизу
вгору, і аж потім те, заради чого все затівалося. Поки кадр
перемальовували раз на подію, це нічого не важило; вікно з грою
просить перемалювання двадцять разів на секунду — і щоразу під ним
наново малювався дифузійний стіл і значки диспетчера програм. Тепер
шукається найвище вікно з рамкою, яке накриває брудний прямокутник
цілком: усе під ним пропускається.

**Ділення на кожен піксель** — про нього вище.

Буфер полотна видає **ядро**, і це не дрібниця оформлення. Спершу його
передавала оболонка зі своєї купи — вікно лишалося чорним, і причина
виявилася в самому пейджингу: `PagingCloneSpace` робить власними стек,
образ програми та **всю купу** (`0x10000000+`). За однією адресою в
батька й дитини лежать різні фізичні сторінки, тож дитина малювала у
свою копію, а оболонка показувала свою — ніким не писану. Тому полотно
живе за `0x7500000`, між буфером редактора й буферами дескрипторів,
тобто у спільній частині простору.

Прохання про запуск і поява задачі рознесені в часі: між ними лежить
усе читання образу з диска. Перша ж спроба це й показала — оболонка
питала «чи жива дитина» кожні сорок мілісекунд, потрапляла в ту щілину
і закривала вікно, поки гра ще вантажилась. Тому запуск позначений
окремим прапорцем `SpawnBusy`, який знімається аж тоді, коли задача
справді існує.

#### Текст програми у вікні

Текстові виклики (`2`, `4`, `6`, `7`, `8`) малюють прямо у фреймбуфер,
повз blit, і полотна не бачать у принципі. Спершу вони працювали як
раніше — і журнал запуску DOOM ліг поверх усієї оболонки. Тоді задачам
із полотном їх заборонили, і текст став просто зникати: програма, яка
лише друкує, у вікні не показувала нічого. Через це діалог запуску
мусив питати «у вікно чи на весь екран», тобто вимагати від
користувача знати те, чого він знати не може, — малює програма
графікою чи друкує.

Тепер такий текст складається в буфер за `0x7D00000` — поруч із
полотном і з тієї ж причини: пише його дитина, а показує батько, тож
лежати він мусить у спільній частині простору. Оболонка бере адресу
заголовка один раз (`syscall 46`) і далі читає довжину й лічильник
змін прямо з пам'яті.

Вікно показує текст, **доки програма не намалювала жодного кадру**.
Намалювала — показує полотно: у графічної програми журнал запуску вже
своє віддав, а в текстової іншого вмісту й не буде. Одне правило
покриває обидва випадки, і питання в діалозі зникло само.

Коли буфер повний, викидається його **перша** половина. Журнал запуску
цікавий на початку, працююча програма — у кінці; половина зберігає
обидва краї краще, ніж будь-яке з двох правил окремо.

Коли програма завершується, вікно **лишається стояти** з останнім, що
вона показала. Спершу воно закривалося тієї ж миті — і через це не
було видно нічого: `HELLO` друкує й виходить за мілісекунди, тож вікно
зникало раніше, ніж устигало намалюватися. Закривається воно тепер
руками, як і належить вікну з результатом.

Обмеження чесні. Вікно одне: ядро вміє сказати лише «дитина жива», а
розрізняти кількох дітей йому нічим. Закрити вікно **живої** програми
не можна — буфер під нею її ж пам'ять; вихід через `Ctrl+Shift+Q`.
`syscall 8` (перелік файлів) лишився відкинутим: він малює готовий
список, а не віддає рядок.

#### TCP

Клієнтський і на одне з'єднання за раз — як і решта підсистем тут.
Стани: `CLOSED → SYN_SENT → ESTAB → DONE`.

Сума рахується з псевдозаголовком. У UDP її дозволено не рахувати
взагалі (у нас там і стоїть нуль), у TCP — ні, тому обійтись як там не
вийшло. Псевдозаголовка в пам'яті не існує: його поля просто додаються
до суми, а довжину доводиться переставляти вручну, бо сума
байт-орієнтована, а не числова.

Вікном оголошуємо рівно те, що ще вміщає буфер. Збрехати більше
означало б попросити даних, які нікуди подіти.

Приймаємо лише те, що точно за порядком: сегмент із чужим номером
відкидаємо, і відправник надішле його ще раз. Черга з дірок коштувала б
окремої структури, а на наших швидкостях не дала б нічого.

Відправка — стоп-і-чекай: сегмент, потім `ACK`, і аж тоді наступний.
Запити, які ми робимо, в один сегмент і вміщаються.

#### Повтори й буфер

Втрачений сегмент більше не означає відмову. `SYN` і дані шлються
повторно — до п'яти разів із паузою в півсекунди. Відлік по **часу**, а
не по обертах циклу: скільки обертів устигне зробити
`NetPollBackground`, залежить від того, чим зайнята машина, а
півсекунди лишаються півсекундою.

Заради цього `TcpSndNxt` більше не рушиться одразу після відправки:
повторний сегмент мусить піти з **тим самим** номером, інакше для того
боку це буде новий шматок, а не повтор загубленого. Номер посувається
аж тоді, коли дані підтвердили.

Підтвердження перевіряється **відніманням**, а не порівнянням «більше
або дорівнює»: номери 32-бітні й переповнюються по колу, і після
переповнення пряме порівняння дало б протилежний висновок.

Приймати повторно не треба нічого: якщо сегмент загубиться, повторить
його відправник, а наш `ACK` просто не посунеться вперед.

Буфер прийому — 256 КБ, і лежить окремою ділянкою, а не масивом у тілі
ядра: `rb` такого розміру fasm заповнив би нулями просто у файлі
образу. Вікном при цьому оголошуємо не більше за 65535 — поле
шістнадцятибітне, хоч би скільки ми вміщали.

#### HTTP

Запит - HTTP/1.0 із заголовком `Host:`. Без нього сервер з іменним
хостингом віддає чужу сторінку або помилку: на одній адресі їх сотні,
і розрізняє їх саме цей рядок. Перша версія команди `Host:` не слала -
і Cloudflare відповідав `403` з кодом `1003`, тобто «за голою адресою
не пускаємо». З заголовком та сама команда дістає `200 OK`.

Версія 1.0 зручна ще й тим, що сервер сам закриває з'єднання, віддавши
відповідь: `FIN` приходить природно, і не треба вгадувати, скільки
байтів чекати.

Хост розрізняється так: спершу пробуємо розібрати як IP, і лише коли не
виходить - питаємо DNS. Інакше `GET 1.1.1.1` пішов би резолвити рядок
«1.1.1.1».

**Чого свідомо немає.** Опцій, включно з MSS. Переупорядкування. Більш
ніж одного з'єднання за раз. І вікна більшого за 64 КБ - для цього
потрібне масштабування вікна, тобто ті самі опції.

#### Як шукали помилки

Три різні речі виглядали однаково — «не вдалося з'єднатись».

Спершу `ParseIp` зберігає й **відновлює** RSI, тому порт розбирався з
початку рядка: замість `80` виходило `10`. З'єднання йшло на порт,
якого ніхто не слухає.

Далі з'ясувалося, що одне повідомлення на всі випадки нічого не
пояснює: воно однаково казало «немає відповіді» й тоді, коли картку не
підняли й пакет навіть не пішов. Причини розділено на п'ять, і
найважливіша з них — `RST`: він означає, що пакет **дійшов** і його
зрозуміли, тобто протокол працює, а закритий лише порт.

Нарешті додано лічильник прийнятих сегментів. Нуль у ньому означає, що
шукати треба в тому, що ми відправляємо, а не в тому, як розбираємо.
Саме він і показав, що `10.0.2.2:80` мовчить не через нашу помилку — на
хості просто ніхто не слухає, а брандмауер відкидає мовчки замість
відмовляти. Перевірка на `1.1.1.1` пройшла з першого разу.

### Редактор

| Клавіша | Дія |
|---|---|
| `F2` | зберегти |
| `F3` | перейти на рядок за номером |
| `ESC` | вийти |
| `↑` `↓` `←` `→` | рух каретки |
| `PgUp` `PgDn` | сторінка вгору / вниз |
| `Home` `End` | початок / кінець рядка |
| `Backspace` | стерти символ перед кареткою |
| `Delete` | стерти символ під кареткою |

У заголовку показано `LINE`, `COL` і `SIZE`. Номер рядка там не для
краси: FASM повідомляє про помилку номером рядка, і `F3` — це спосіб
одразу туди дістатись.

> **Що тут було раніше.** Буфер редактора був статичним масивом на
> 32 КБ у тілі ядра, а файл більший за нього **мовчки обрізався** при
> відкритті — тобто `kernel.asm` (понад 280 КБ) відкривався на 11 % і
> збереження знищувало решту. Довжина тексту шукалась за нульовим
> байтом, тому нуль усередині файлу теж обрізав його без попередження.
>
> Гірше було інше: змінна `EditorCursor` була одночасно і позицією
> запису, і кінцем тексту. Символи дописувались тільки в кінець,
> `Backspace` стирав тільки останній, а стрілки рухали **екран**, а не
> каретку. Редагувати всередині файлу було неможливо в принципі — це
> був не редактор, а друкарська машинка з прокруткою.
>
> Тепер довжина (`EdLen`) і каретка (`EditorCursor`) роздільні, вставка
> й видалення працюють у довільному місці через зсув хвоста, а буфер
> винесено з тіла ядра в окрему ділянку на 4 МБ за адресою `0x7100000`
> — між мережевими буферами і буферами файлових дескрипторів. Ядро від
> цього навіть схудло на 32 КБ.

**Двійкові файли.** Якщо у файлі трапляється нульовий байт, редактор
відкриває його **лише на перегляд** і фарбує смугу заголовка в
темно-червоне: `BINARY FILE - READ ONLY`. Раніше довжина шукалась саме
за нулем, тому бінарник просто обривався на першому ж і виглядав
коротким і нешкідливим. Тепер файл вантажиться повністю — і без цього
захисту `EDIT KERNEL.BIN` відкрив би ядро на редагування, де один
випадковий символ і `F2` зіпсували б його остаточно.

> **Кирилиця в редакторі не видно.** Шрифт ядра покриває лише ASCII
> 32–126, тому україномовні коментарі в `kernel.asm` показуються
> порожнечею. Код правити можна, коментарі — читати ні. Це не заважає
> самокомпіляції, але робить редагування всліпу там, де пояснення
> найпотрібніші.

## Графічна оболонка

Запускається з текстової консолі:

```
RUN GUI.BIN
```

> Саме `RUN`, не `OPEN`. Команда `OPEN` віддає будь-який `.BIN` програвачу
> відео і намагається виконати картинку як програму.

Вихід назад у консоль — `File → Exit Windows` у диспетчері програм.

### Чому знадобилася перебудова

Спочатку віконного інтерфейсу було два, написані з різницею в три місяці:

- `libgui/gui.c` — новий шар рендеру з частковим оновленням екрана,
  пропорційним шрифтом і чергою подій. Ним користувалася лише демка;
- `userland/shell.c` — справжня оболонка з власним шрифтом на 64 гліфи
  (тільки великі літери), власним буфером кадру і повним виведенням
  усього екрана щокадру.

Поведінка вікна в оболонці була гілкою `if/else` **всередині циклу
рендеру**, тому кожен новий додаток означав правку рендерера, а вся
робота над частковим оновленням екрана оболонці не діставалася.

Обидва шари злито в один. Розділення тепер таке саме, як у Windows 3.1:
`GDI` окремо від `USER`.

### Вікно як об'єкт

Основа — процедура вікна. Все, що вона не обробила, падає у
`def_window_proc`, який малює рамку, заголовок, кнопки, смуги прокрутки,
веде перетягування й зміну розміру.

```c
/* Було: поведінка вікна = гілка в рендерері */
if (w->app_type == APP_CONSOLE)       { ...малюємо консоль... }
else if (w->app_type == APP_EDITOR)   { ...малюємо редактор... }
else if (w->app_type == APP_EXPLORER) { ...малюємо провідник... }

/* Стало: поведінка вікна = його власна процедура */
static long console_proc(Window* w, int msg, long a, long b) {
    switch (msg) {
    case WM_PAINT:   ...; return 0;
    case WM_CHAR:    ...; return 0;
    case WM_COMMAND: ...; return 0;
    }
    return def_window_proc(w, msg, a, b);
}
```

Новий додаток — це одна функція плюс виклик `wnd_create`. Рендерер
чіпати не треба.

З цієї ж конструкції безкоштовно виростають елементи керування: кнопка,
поле вводу і список — теж вікна, з тим самим фокусом, обрізанням і
частковим перемальовуванням.

### Модель малювання

Ніхто не малює «зараз». Замість цього ділянка позначається недійсною, а
раз за кадр менеджер обходить порядок вікон знизу вгору й перемальовує
**лише перетин** недійсної ділянки з кожним вікном:

```
wm_pump():
  1. зняти курсор із буфера кадру
  2. розібрати події від ядра і роздати вікнам
  3. перемалювати недійсні ділянки, знизу вгору
  4. покласти курсор назад і вивести на екран лише змінене
```

Пункти 1 і 3 не можна міняти місцями: курсор лежить у тому самому
буфері кадру, і якщо малювати під ним, він розмажеться слідом по екрану.

Перетягування вікна не перемальовує вміст узагалі — тягнеться `XOR`-контур,
як робила Windows 3.1, а геометрія застосовується на відпусканні.

### Піктограми

Окремого формату `.ICO` немає. Поклали поряд із програмою файл із тим
самим іменем — `APP.BIN` → `APP.BMP` — і він став її значком. Для самих
`.BMP` піктограмою є вони самі. Картинки більші за 128×128 як значок не
беруться.

BMP розбирається **у програмі**, а не в ядрі: ядро вміє показати картинку
лише командою `OPEN` на весь екран, а вікну потрібні дані, щоб обрізати
їх по межах і масштабувати. Нових системних викликів для цього не
знадобилося — розмір береться з самого заголовка BMP.

Підтримано нестиснений BMP на 1, 4, 8, 24 і 32 біти, з палітрою, знизу
вгору і зверху вниз. `RLE` не підтримується.

### Обмеження оболонки

| Обмеження | Причина |
|---|---|
| Усі вікна — один процес | у ядрі дві задачі, одночасно жива лише одна програма |
| Запуск програми = ланцюжок | оболонка йде, програма працює, ядро повертає оболонку назад |
| Немає комбінованого списку і MDI | ще не зроблено |
| Немає перетягування файлів | ще не зроблено |

## Самокомпіляція

Система містить порт flat assembler і здатна асемблювати власне ядро.

### Підготовка

1. Завантаж вихідники fasm (https://flatassembler.net)
2. Скопіюй **14 файлів `.INC`** з папки `SOURCE\` у `fasm-port\`:

```
ASSEMBLE.INC  AVX.INC       ERRORS.INC    EXPRCALC.INC
EXPRPARS.INC  FORMATS.INC   MESSAGES.INC  PARSER.INC
PREPROCE.INC  SYMBDUMP.INC  TABLES.INC    VARIABLE.INC
VERSION.INC   X86_64.INC
```

> **`SYSTEM.INC` з `SOURCE\` не копіювати.** Він Linux-ний, і саме його
> замінює наш порт. Якщо перезаписати — збірка або впаде, або дасть
> бінарник, який у QEMU піде в triple fault.

3. `BUILD_FASM.bat` → `FASM.BIN`
4. Скопіювати `FASM.BIN` у корінь `E:\`

### Використання

```
RUN FASM.BIN HELLO.ASM HELLO.BIN
RUN HELLO.BIN
```

Повний цикл перезбірки ядра, не виходячи з системи:

```
EDIT KERNEL.ASM            правимо джерело
RUN FASM.BIN KERNEL.ASM K.BIN
INSTALL K.BIN              ставимо ядром
REBOOT
```

`INSTALL` спершу відкладає поточне `KERNEL.BIN` у `KERNEL.BAK` і лише
потім кладе на його місце нове. Якщо резервна копія не записалась —
не змінюється нічого. Відкотитись із робочої системи можна звичайним
`COPY KERNEL.BAK KERNEL.BIN`.

> **Застереження.** Резервна копія рятує лише доти, доки система
> завантажується: щоб виконати `COPY`, потрібна робоча оболонка. Якщо
> нове ядро не стартує, повернути старе можна тільки ззовні. Пункт
> завантажувача для вибору `KERNEL.BAK` закрив би цю дірку, але
> завантажувач наразі змінам не підлягає.

### Що перевірено

Протокол, знятий на копії диска в QEMU:

| Крок | Результат |
|---|---|
| `EDIT KERNEL.ASM` на джерелі 302 746 Б | відкрився повністю, `SIZE 302746` у заголовку |
| `F3` → рядок 4745 | каретка стала на потрібний рядок, `LINE 4745 COL 1` |
| 39 × `→`, `Delete`, ввід `3` | `Version 2.0` → `Version 3.0` **у середині файлу** |
| `F2` | збережено, розмір не змінився |
| `RUN FASM.BIN KERNEL.ASM K.BIN` | `4 passes, 47960 bytes` |
| `INSTALL K.BIN` | `INSTALLED. PREVIOUS KERNEL SAVED AS KERNEL.BAK` |
| `REBOOT` | система стартувала з написом `EUGENE OS  Version 3.0` |
| порівняння `KERNEL.BAK` з еталоном | побайтово збігається з попереднім ядром |

Окремо перевірено відповідність еталонному інструментарію: те саме
джерело, зібране всередині ОС і віндовим fasm, дає **побайтово
однакові** файли (`cmp` мовчить на 78 712 байтах).

### Межі самокомпіляції

Самозбирається **ядро і програми на асемблері**. Сі-частина
(`GUI.BIN`, `libgui`, `userland/shell.c`) вимагає GCC, `ld` і
`objcopy` — компілятора C в системі немає, тому графічна оболонка
збирається лише на основній машині. Завантажувач теоретично
асемблюється, але встановити результат нікуди: `EFI\BOOT\BOOTX64.EFI`
лежить у підкаталозі, а ні порт fasm, ні `COPY` з підкаталогами не
працюють.

### Що довелося переписати в порті

**Аргументи командного рядка.** У Linux `argv` лежить на стеку готовим
масивом. У нас ядро віддає один рядок через syscall 21, тому
`build_command_line` сам ріже його на слова і будує такий самий масив
`[count][argv0][argv1]...`. Після цього весь код розбору параметрів fasm
працює без змін, включно з опціями `-m`, `-p`, `-d`, `-s`.

**Пам'ять.** Немає `brk`/`mmap`, тому `init_memory` віддає фіксований
регіон 64 МБ за адресою 192 МБ.

**`MODES.INC` перевизначає `push`/`pop` як 32-бітні** — це його основне
призначення: ядро fasm 32-бітне, і його `push eax` має класти 4 байти.
Тому в `SYSTEM.INC` **не можна писати `push rbx`** — 64-бітні регістри
зберігаються через `r10`–`r15` або змінні в пам'яті.

**Локальні мітки мають префікси `eug_` і `gp_`** — у ядрі fasm 3179
глобальних міток, і без префіксів збіг імен майже гарантований.

## Мережа

### Налаштування QEMU

```
-netdev user,id=n0 -device rtl8139,netdev=n0,mac=52:54:00:12:34:56
-object filter-dump,id=dump0,netdev=n0,file=net.pcap
```

Режим `user` — це NAT: не потребує прав адміністратора, вихідні з'єднання
працюють. Пінг **з хоста в гостя** в цьому режимі неможливий, для нього
потрібен `tap`.

`filter-dump` пише весь трафік у `net.pcap` — відкривається у Wireshark.
Це головний інструмент налагодження: видно точно, які байти пішли в мережу.

### Чому RTL8139

Працює через порти вводу-виводу, а не через відображену пам'ять, і має
**один суцільний кільцевий буфер прийому** замість дескрипторних кілець,
як в e1000. Для першого драйвера це вдвічі менше коду.

### Тонкощі драйвера

**Bus Mastering обов'язковий.** У регістрі `0x04` конфігураційного простору
PCI треба виставити біт 2. Без нього карта не має права писати в пам'ять —
драйвер виглядатиме робочим, але буфер прийому завжди буде порожній.

**Запас у буфері прийому.** Карті оголошуємо 8 КБ, а відводимо 16 КБ. При
`WRAP=1` карта не обриває кадр на межі буфера, а пише за його кінець.
Без запасу вона затерла б сусідню пам'ять.

**У `CAPR` пишеться позиція мінус 16.** Апаратна особливість чіпа. Якщо
записати справжнє зміщення, карта почне псувати власний буфер — причому
спочатку все виглядатиме робочим і зламається на кількадесятому кадрі.

**Полінг замість переривань.** `NetPollBackground` викликається в головному
циклі ядра, тому система відповідає на ARP і пінг у фоні. Так простіше й
безпечніше, ніж чіпати PIC.

### Контрольні суми

Складаємо дані як 16-бітні слова у 32-бітний акумулятор, згортаємо переноси,
інвертуємо. **Порядок байтів не має значення** — додавання симетричне, тож
читаємо слова так, як вони лежать у пам'яті, і результат кладемо так само.

### Якщо DNS не працює

У режимі `user` QEMU проксює DNS-запити гостя через системний резолвер
хоста. Якщо DNS хоста зламаний — у гостя теж нічого не буде. Перевірити
можна командою `nslookup` у PowerShell на хості; обійти —
`SETDNS 8.8.8.8`.

## Карта пам'яті

| Адреса | Розмір | Призначення |
|---|---|---|
| `0x0100000` | 1 МБ | ядро |
| `0x1000000` | 16 МБ | буфер завантаження файлів |
| `0x2000000` | 32 МБ | буфер читання каталогів |
| `0x3000000` | 48 МБ | буфер рендеру |
| `0x3FFFFF8` | — | вершина стеку програм |
| `0x4000000` | 64 МБ | програми користувача |
| `0x5000000` | 28 МБ | купа ядра |
| `0x7000000` | 24 КБ | буфери мережевої карти |
| `0x7100000` | 4 МБ | буфер редактора |
| `0x8000000` | 64 МБ | буфери файлових дескрипторів |
| `0xC000000` | 64 МБ | робоча пам'ять fasm |
| `0x10000000` | 128 МБ | купа програм користувача |
| `0x18000000` | 127 МБ | пул кадрів розподільника |

Окремо, поза цією таблицею, лежать дрібні службові області:
`0x200000` — блок відомостей від завантажувача з картою пам'яті UEFI,
`0x300000` — бітова карта вільних кадрів, `0x3D00000` — буфер рядка
програвача відео.

Дві останні позиції таблиці змінили природу. **Купа програм більше не
є фізичною областю**: вона підкачується на вимогу, і кадри під неї
беруться з пулу. **Пул** — це те, чим розпоряджається розподільник
кадрів; він починається з 384 МБ, бо нижче кожна адреса вже комусь
належить за цією таблицею.

Відображення тотожне — **фізична адреса дорівнює віртуальній** — крім
двох вилучених сторінок і вікна програми, яке в кожної задачі своє.
Тотожність спрощує DMA: буфер віддається карті напряму, без трансляції.
Докладніше — у розділі про сторінкові таблиці.
> **Купа програм лежить на 256 МБ, і це не випадково.** Раніше вона
> починалася з `0x8000000` — рівно там, де ядро тримає буфери файлових
> дескрипторів. Програма, яка водночас виділяла пам'ять і тримала
> відкритий файл, затирала власні дані. Значення дублюється у
> `libc/eugene_libc.c` (`HEAP_START`) — при зміні правити в обох місцях.

> **`AppStackTop` дорівнює `0x3FFFFF8` і НЕ кратний 16 — це навмисно.**
> SysV ABI вимагає вирівнювання 16 байт **перед інструкцією `call`**, а
> отже на вході у функцію `RSP % 16 == 8`, бо `call` уже поклав адресу
> повернення. Ядро заходить у програму через `iretq`, без `call`, тому
> мусить подати саме таке значення. Спроба «виправити» це на `0x3FFFFF0`
> зсуває весь стек на 8 байтів, і кожен `movaps` по стеку в програмах,
> зібраних із SSE, дає `#GP`.

## Завантажувач

`boot/main.asm` — власний UEFI-застосунок (`format PE64 EFI`), який
піднімає `EFI_GRAPHICS_OUTPUT_PROTOCOL`, малює екран налаштувань прямо у
фреймбуфер (жодного тексту через `ConOut`), збирає дані про процесор,
пам'ять і диск, дає меню з трьох пунктів і завантажує ядро.

### Зміщення в таблиці Boot Services

`EFI_BOOT_SERVICES` починається з `EFI_TABLE_HEADER` на 24 байти
(`Signature` 8 + `Revision` 4 + `HeaderSize` 4 + `CRC32` 4 + `Reserved` 4),
далі — покажчики на функції по 8 байтів кожен. Звідси:

| Зміщення | Функція |
|---|---|
| `0x28` | `AllocatePages` |
| `0x38` | `GetMemoryMap` |
| `0x48` | `FreePool` |
| `0x98` | `HandleProtocol` |
| `0xE8` | `ExitBootServices` |
| `320` | `LocateProtocol` |

У коді ці числа винесені в іменовані константи (`BS_GET_MEMORY_MAP`,
`BS_EXIT_BOOT_SERVICES` і так далі). Причина — нижче.

### Випадок: `ExitBootServices`, який не викликався

Найдовший баг проєкту. Наводиться повністю, бо він добре показує, чому в
UEFI помилка може роками не мати жодного симптому.

**Симптом.** На екрані налаштувань завжди світилося `RAM SIZE : UNKNOWN`,
хоча процесор і розмір диска визначалися правильно. Дрібниця, на яку
півроку ніхто не дивився.

**Гіпотеза.** `GetRamInfo` виходить по гілці `test rax, rax / jnz .done`,
тобто виклик повертає ненульовий статус. Але який саме виклик? У коді
стояло голе `[rax + 0x28]`, і за припущенням це мав бути `GetMemoryMap`.
Якщо припущення хибне, то за цим зміщенням лежить сусідня функція
таблиці — `AllocatePages`.

**Метод.** У копію завантажувача вбудований зонд: обидва зміщення
викликаються з коректними аргументами `GetMemoryMap`, а повернутий статус
і отриманий `DescriptorSize` виводяться просто на екран налаштувань.
Образ записується в копію VHD, запускається в QEMU з `snapshot=on`, екран
знімається через `screendump` монітора.

**Доказ.**

```
BS+28 ST/DS: 2/0     <- AllocatePages: статус 2, DescriptorSize не заповнений
BS+38 ST/DS: 0/48    <- GetMemoryMap:  статус 0, DescriptorSize 48
```

Статус 2 — це `EFI_INVALID_PARAMETER`: `AllocatePages` отримав адреси
замість типу розподілу й чесно відмовився. Розмір дескриптора 48 байтів —
канонічне значення `EFI_MEMORY_DESCRIPTOR`. Отже зміщення в коді були
зсунуті рівно на одну функцію.

**Наслідки.** Перший — той самий `RAM SIZE : UNKNOWN`. Другий значно
серйозніший: у циклі виходу за зміщенням `0x38` викликався `GetMemoryMap`
замість `ExitBootServices`, тобто **служби завантаження не вимикалися
жодного разу за всю історію проєкту**. Ядро стартувало поверх живої
прошивки.

**Чому це не проявлялося.** Ядро одразу після отримання керування ставить
власні GDT і IDT та перепрограмовує контролер переривань. Прошивка після
цього фізично не має способу отримати керування назад: її обробники
відключені, її сторожовий таймер не має через що спрацювати. Вона
лишалася формально живою, але цілком інертною.

**Що це реально коштувало.** Карта пам'яті ніколи не читалася, тобто ядро
не знало, які регіони прошивка тримає під собою, і розкладало свою купу
за фіксованими адресами наосліп. У QEMU не збіглося. Це рівно той клас
дефектів, який працює в емуляторі й падає на живому залізі.

**Виправлення.** Правильні зміщення, винесені в іменовані константи;
цикл `GetMemoryMap` + `ExitBootServices` з повтором (бо `MapKey` протухає
від будь-якої зміни карти пам'яті) і обмеженням у 16 спроб; перевірка
статусу на кожному кроці.

**Підтвердження.** Чотири сценарії на копіях диска:

| Сценарій | Очікувано | Фактично |
|---|---|---|
| Екран налаштувань | реальний обсяг RAM | `RAM SIZE : 448 MB` |
| Завантаження ядра | консоль ОС | запрошення `C:/>` |
| `RUN GUI.BIN` | графічна оболонка | Program Manager + Console |
| `KERNEL.BIN` перейменовано | зрозуміла відмова | `EFI STATUS: 14` (`EFI_NOT_FOUND`) |

**Висновок.** У UEFI немає жодного захисту від такої помилки: невірне
зміщення дає валідний покажчик на іншу функцію, вона повертає код
помилки, а код помилки ніхто не перевіряє. Саме тому у виправлення
входять не лише правильні числа, а й іменовані константи та обов'язкова
перевірка статусу — щоб наступного разу дефект кричав, а не мовчав.

### Вибір відеорежиму

Це те місце, де завантажувач перестає *спостерігати* за GOP і починає
ним *керувати*. З чотирьох функцій протоколу задіяні три:
`QueryMode`, `SetMode` і структура `Mode`.

**Перелік.** На старті `EnumModes` читає `Mode->MaxMode` і по черзі
питає `QueryMode` про кожен номер. Для кожного режиму зберігаються
чотири числа: ширина, висота, крок рядка, формат пікселя. `QueryMode`
сам виділяє буфер під `MODE_INFORMATION` і віддає його у власність
викликача, тому кожен звільняється через `FreePool`.

**Вибір.** Пункт меню `[ 2 ] SELECT VIDEO MODE` відкриває список:

```
EUGENE OS - GOP VIDEO MODES
ARROWS SELECT, ENTER APPLY, ESC BACK

[ 0 ] 1280X800   STRIDE 1280  FMT 1  <-- ACTIVE
[ 1 ] 640X480    STRIDE 640   FMT 1
[ 2 ] 800X480    STRIDE 800   FMT 1
...
[ 29 ] 2560X1600 STRIDE 2560  FMT 1
```

**Застосування.** `SetMode` міняє не лише роздільність: змінюється крок
рядка і **адреса фреймбуфера**. Тому після успішного виклику всі дані
екрана перечитуються заново (`ReadGopMode`), і лише потім екран
малюється. Саме через це відмальовку винесено в окрему процедуру
`DrawSetupScreen`. Якщо прошивка відмовляє — старий режим лишається
цілим, а на екрані з'являється `FIRMWARE REFUSED SETMODE`.

Вибраний режим доживає до ядра: ширина, висота і крок передаються у
`RDX`, `R8`, `R9`, і вся ОС разом із графічною оболонкою працює на тій
роздільності, яку вибрали в завантажувачі.

**Що показав перелік у QEMU.** 30 режимів від 640×480 до 2560×1600.
У всіх без винятку крок рядка дорівнює ширині, і у всіх формат пікселя
дорівнює 1 (`PixelBlueGreenRedReserved8BitPerColor`, тобто BGRA). Це
підтверджує два припущення, на яких мовчки трималося малювання, і
водночас пояснює, чому помилка з кроком рядка не могла проявитися на
цьому стенді: QEMU просто ніколи не вирівнює рядки.

### Порядок каналів пікселя

`MODE_INFORMATION+12` містить `EFI_GRAPHICS_PIXEL_FORMAT` — і донедавна
код його просто не читав, мовчки припускаючи формат 1. На цьому стенді
припущення було правильним, але припущення — не гарантія.

| Значення | Формат | Що це означає |
|---|---|---|
| 0 | `PixelRedGreenBlueReserved` | у пам'яті молодшим байтом іде червоний |
| 1 | `PixelBlueGreenRedReserved` | молодшим байтом синій — наш звичний `0x00RRGGBB` |
| 2 | `PixelBitMask` | прошивка дає власні маски в `PixelInformation` |
| 3 | `PixelBltOnly` | **лінійного фреймбуфера немає взагалі** |

**Як зроблено переведення.** Весь код завантажувача задає кольори як
`0x00RRGGBB` — так їх зручно читати. Переклад у нативний порядок робить
`MapColor`, і робить його **один раз на заливку або на рядок тексту**, а
не на кожен піксель: `FillScreen` переводить колір перед `rep stosd`, а
`DrawString_Color` — перед циклом по символах (`DrawChar` кличеться лише
звідти, тому далі по ланцюжку колір уже нативний). Внутрішні цикли
малювання не змінилися взагалі.

Для `PixelBitMask` зсуви кожного каналу рахуються один раз у
`ReadGopMode` через `BSF` по масках, а не шукаються заново на кожному
кольорі.

**`PixelBltOnly` — окремий випадок.** Це не питання порядку байтів: у
такому режимі прямого доступу до відеопам'яті просто немає, малювати
можна лише через `Blt()`, а `FrameBufferBase` не має сенсу. Уся наша
графіка — і завантажувача, і ядра — пише у фреймбуфер напряму, тому
режим непридатний. Але завантажувач не здається одразу: `FindLinearMode`
шукає в переліку перший режим із лінійним буфером і перемикається на
нього через `SetMode`. Лише якщо таких немає жодного — повідомлення
`NO LINEAR FRAMEBUFFER MODE` через `ConOut` і зупинка. У списку режимів
такі варіанти теж відхиляються ще до `SetMode`, з поясненням на екрані.

**Як перевірено, якщо QEMU дає лише BGR.** Формат був примусово
виставлений у 0 в копії завантажувача, і виміряно, що вийшло на екрані:

| Задумано `0x00RRGGBB` | Норма (BGR) | Примусовий RGB |
|---|---|---|
| `0x0000AA` фон | синій | `#AA0000` червоний |
| `0xFFFF00` жовтий | жовтий | `#00FFFF` блакитний |
| `0xFF0000` червоний | червоний | `#0000FF` синій |
| `0x00FF00` зелений | зелений | `#00FF00` без змін |
| `0xFFFFFF`, `0xAAAAAA`, `0x555555` | сірі | без змін |

Червоний і синій міняються місцями, зелений і вся сіра шкала лишаються
на місці — тобто перестановка відбувається рівно там, де має.

### Вимірювання

Пункт меню `[ 3 ] RUN BENCHMARKS` міряє сам себе і показує результат на
екрані. Годинник — лічильник тактів процесора (`RDTSC`), єдиний, що
доступний і до, і після `ExitBootServices`. Сам по собі він
безрозмірний, тому калібрується один раз об `Stall()` з Boot Services:
просимо прошивку зачекати 100 мс і дивимось, скільки тактів минуло.
Кожен вимір проганяється кілька разів і усереднюється.

**Результат на стенді** (QEMU 10.2, TCG, OVMF, 1280×800, ядро 78 712 Б):

| Що | Час |
|---|---|
| Калібрування | 2689 тактів на мікросекунду |
| `LocateProtocol` + читання режиму | 107 мкс |
| Перелік 30 режимів (`QueryMode` × 30) | 203 мкс |
| Дані про процесор, пам'ять і диск | 306 мкс |
| Відмальовка екрана налаштувань | 1889 мкс |
| **Разом до першого екрана** | **2508 мкс** |
| Заливка екрана, прямий запис | 1630 мкс |
| Заливка екрана, `Blt` `EfiBltVideoFill` | 1376 мкс |
| `Open` + `GetInfo` + `Read` ядра | 7773 мкс |

**Що з цього випливає.**

*Робота з GOP майже безкоштовна.* Підняти протокол і прочитати режим —
107 мкс; перелічити всі тридцять режимів — 203 мкс, тобто близько 7 мкс
на один `QueryMode` разом із `FreePool`. Разом це 12 % часу до першого
екрана. Перелік режимів на кожному завантаженні виправданий: він не
коштує практично нічого.

*Головна витрата — малювання.* Відмальовка екрана налаштувань займає
1889 мкс, тобто 75 % усього старту. З них 1630 мкс — сама заливка фону,
і лише близько 260 мкс — увесь текст. Тобто вузьке місце не в протоколах
UEFI і не в шрифті, а в одному проході по мільйону пікселів.

*Читання ядра дорожче за все інше разом.* 7773 мкс проти 2508 мкс на весь
старт — утричі більше. Це приблизно 10 МБ/с через ланцюг
`SimpleFileSystem` емульованого диска. Повний шлях від старту до передачі
керування ядру виходить близько 10 мс.

**Про порівняння прямого запису з `Blt`.** Тут результат вийшов
протилежний очікуваному: `Blt` не повільніший, а на 16 % швидший за
прямий запис. Але саме цьому числу вірити не можна, і це головний
висновок виміру. Під TCG фреймбуфер — не шина PCIe, а звичайна ділянка
пам'яті емулятора з відстеженням змінених сторінок. Порівнюються не два
способи дістатися до відеопам'яті, а два згенеровані емулятором цикли:
наш `rep stosd` проти внутрішнього циклу OVMF. На живому залізі
фреймбуфер — некешована MMIO-область, і картина там визначається зовсім
іншими чинниками.

Тобто цей вимір має від'ємну доказову силу: він показує, що **питання
неможливо закрити на емуляторі**, і саме тому потребує іншого стенда.

**Чого цим стендом не виміряти взагалі:**

- прямий запис проти `Blt` — потрібна реальна шина до відеопам'яті;
- випадок, коли крок рядка не дорівнює ширині — QEMU ніколи не вирівнює
  рядки, у всіх 30 режимах крок збігається з шириною;
- порядок каналів, відмінний від BGR — у всіх 30 режимах формат 1;
- таблиці режимів різних виробників прошивок — тут лише OVMF.

**Порівняння з іншими завантажувачами.** Порівнювати по швидкості на
цьому стенді сенсу немає, тому порівняння тут — за тим, що стосується
теми: як фреймбуфер потрапляє до ядра.

| Завантажувач | Що робить із графікою |
|---|---|
| `systemd-boot` | графіки не торкається, лише передає керування EFI-заглушці |
| GRUB2 | має власну відеопідсистему, GOP — один із її драйверів; ядро отримує фреймбуфер тегом протоколу Multiboot2 |
| Limine | сам ставить режим і віддає опис фреймбуфера у структурі власного протоколу |
| EugeneOS | сам ставить режим через `SetMode` і віддає базу, ширину, висоту й крок у чотирьох регістрах |

Різниця не в тому, хто швидший, а в кількості проміжних шарів: у нас між
`QueryMode` і першим пікселем, який малює ядро, немає нічого.

### Завантаження ядра

1. `HandleProtocol` → `EFI_LOADED_IMAGE` → `EFI_SIMPLE_FILE_SYSTEM`;
2. `OpenVolume`, потім `Open("kernel.bin")` у режимі читання;
3. **`GetInfo`** з `EFI_FILE_INFO_GUID` — справжній розмір файлу з поля
   `FileSize` (зміщення 8);
4. **`AllocatePages`** з типом `AllocateAddress` на `0x100000` — рівно
   стільки сторінок, скільки треба під цей розмір;
5. `Read`, після чого прочитана кількість звіряється з розміром файлу;
6. `Close`, гасіння екрана, цикл `GetMemoryMap` + `ExitBootServices`.

Кожен крок перевіряє статус. Раніше не перевірявся жоден: розмір просили
«мегабайт і сподіваємось», адреса `0x100000` бралася на віру без жодного
резервування, а відсутній `kernel.bin` призводив до стрибка на те, що
випадково лежало за цією адресою.

### Діагностика поразок

Замість `jmp $` на чорному екрані завантажувач малює причину:

```
*** BOOT FAILURE ***
KERNEL.BIN NOT FOUND ON BOOT VOLUME
EFI STATUS:      14
SYSTEM HALTED. POWER OFF AND RESTART.
```

Показується змістовна частина коду `EFI_STATUS` (2 — невірний параметр,
5 — замалий буфер, 14 — не знайдено). Єдиний виняток — падіння самого
GOP: фреймбуфера тоді ще немає, тому повідомлення йде в `ConOut` рядком
UTF-16. У шрифті завантажувача лише коди 32–93, тому всі діагностичні
рядки — великими літерами.

## Передача керування ядру

Завантажувач передає ядру чотири значення в регістрах:

| Регістр | Значення |
|---|---|
| `RCX` | базова адреса фреймбуфера від GOP |
| `RDX` | ширина — скільки пікселів **видно** в рядку |
| `R8` | висота |
| `R9` | **крок рядка** — скільки пікселів перескочити до наступного |
| `R10` | блок відомостей із картою пам'яті UEFI, або 0 |

> **Ширина і крок — різні числа.** Специфікація UEFI дозволяє прошивці
> повернути `PixelsPerScanLine` більшим за горизонтальну роздільність:
> рядки можуть бути вирівняні. Ширина потрібна для обрізання й
> центрування, крок — для будь-якої адресації пікселя. У QEMU вони
> збігаються, тому плутанина довго не проявлялася; на залізі, де вони
> різні, зображення поїде діагональним зсувом.
>
> Ядро має захист: якщо `R9` менший за ширину (старий завантажувач його
> не передавав), крок вважається відсутнім і береться рівним ширині.

### Сторінкові таблиці

У довгому режимі пейджинг **не можна вимкнути**: без нього процесор
випадає з режиму. Тому питання не в тому, чи він є, а в тому, чиї
таблиці діють.

Досі діяли таблиці прошивки, успадковані через `ExitBootServices`. Вони
лежать у пам'яті, яку після виходу зі служб сама ж прошивка вважає
вільною, — тобто ядро виконувалось на структурах, які могло затерти
власним розподільником.

Тепер ядро будує свої: тотожне відображення 0…4 ГБ сторінками по 2 МБ,
шість кадрів. Діапазон обраний не за обсягом пам'яті — вона
закінчується на 511 МБ, — **а тому, що фреймбуфер сидить на 2 ГБ**, у
дірі PCI. Вужче відображення лишило б систему без екрана.

Гігабайти 2 і 3 позначені `PCD`, тобто некешованими. Там немає пам'яті,
там регістри пристроїв, і кешований запис у них дійшов би тоді, коли
кеш вирішить, а не коли ми написали.

### Дві недоступні сторінки

Тотожне відображення означає, що адреса є всюди. Дві сторінки з нього
навмисно **вилучено** — саме там, де помилка інакше лишається тихою.

| Адреса | Що ловить |
|---|---|
| `0x00000000` | розіменування нульового покажчика |
| `0x03E00000` | переповнення стека програм |

Вимкнути одну сторінку 4 КБ усередині сторінки 2 МБ не можна — тільки
замінити всю сторінку таблицею з 512 записів. Наслідок, про який варто
пам'ятати: стек програми обмежено приблизно двома мегабайтами.

Перевірити обидві: команди `NULLTEST` і `PFTEST`. Обидві навмисно
валять систему й вимагають перезавантаження — це їх призначення.
`PFTEST` читає рівно з 4 ГБ, першої адреси за межею відображення, і
заразом підтверджує, що межа саме там.

### Розподільник кадрів

Роздає сторінки по 4 КБ з пам'яті **вище 384 МБ**. Нижче кожна адреса
вже комусь належить за картою пам'яті, і перелічувати їх усередині
розподільника означало б завести другий опис тієї самої карти, який
роз'їдеться з першим при першій же зміні константи.

Будується у два проходи: спершу знаходимо, де закінчується придатна
пам'ять, потім позначаємо **все зайнятим** і звільняємо лише те, що
прошивка назвала придатним. Помилитися в бік «зайнято» безпечно, у бік
«вільно» — ні, тому напрям саме такий.

Кадр віддається **обнуленим**. Це не ввічливість: під сторінкові
таблиці інакше не можна, бо сміття в невикористаних записах процесор
тлумачить як справжні відображення.

### Підкачка на вимогу

128 МБ під купу програми — це претензія на адресний простір, а не
використання: оболонка чіпає близько чотирьох мегабайтів. Тому таблиці
під купу створюються, а сторінки в них лишаються **відсутніми**. Кадр
з'являється в мить першого звернення.

Те саме зроблено з вікном програми — стеком і образом. Ядро більше не
виділяє під образ пам'ять наперед: воно просто пише за адресою 64 МБ, і
сторінки виникають самі.

Межа законного **вузька навмисно**. Виділяти кадр на будь-яку відмову
означало б втратити все, заради чого ставилися нульова сторінка й
вартовий: справжня вада програми тихо отримала б пам'ять і поїхала
далі. Тому перевірок чотири — вектор, біт присутності в коді помилки,
діапазон, наявність запису каталогу, — і кожна відсікає свій випадок.

Результат видно командою `TASKS`: `HEAP PAGES MAPPED` показує, скільки
сторінок програма справді зачепила. Для оболонки це близько тисячі —
чотири мегабайти замість ста двадцяти восьми.

### Власний адресний простір на задачу

Усі програми злінковані на `0x4000000`, і змінити це не можна: на диску
лежать готові бінарники без вихідних текстів. Дві програми в пам'яті
одночасно не помістилися б — обидві вважають, що займають ту саму
адресу.

Пейджинг знімає це питання без жодної зміни в програмах. Кожна задача
отримує власні `PML4`, `PDPT` і `PD0`, у яких віртуальна адреса 64 МБ
веде на **інші фізичні кадри**. Оболонка й гра обидві мають рацію — у
своїх просторах.

Приватними стають лише три групи записів каталогу: стек, образ і купа.
Решта спільна, і це принципово — там ядро, його стек, буфери й бітова
карта кадрів. Підмінити зайвий запис означало б відібрати в ядра
власний код посеред роботи.

> **`CR3` і `RSP` перемикаються сусідніми інструкціями, без жодного
> звернення до стека між ними.** Після зміни `CR3` діє вже новий
> простір, а `RSP` іще вказує на стек попередньої задачі, якого в
> новому просторі може не бути. Будь-який `push`, `call` чи переривання
> в цю мить дає відмову сторінки на неіснуючому стеку — тобто подвійну
> помилку й перезавантаження без жодного повідомлення.
>
> Те саме правило діє ширше: **дія, виконана в одному просторі, а
> потрібна в іншому, не працює**. Обидва падіння під час розробки цього
> механізму були саме такими. Образ програми завантажувався в ядерному
> просторі, а потрібен був у просторі задачі. Початковий кадр задачі
> будувався в ядерному просторі, а стек програми вже був приватним — і
> задача стартувала з порожнім стеком.

Пам'ять задачі повертається в пул **повністю**: спершу сторінки
всередині таблиць, потім самі таблиці, потім каталог, `PDPT` і `PML4`.
Порядок саме такий — звільнивши таблицю першою, ми втратили б перелік
сторінок, які вона описує.

Звільнення робиться **не в самому виході**: у ту мить ядро стоїть на
стеку задачі, яку звільняє. Усі три шляхи виходу — звичайний, аварійне
вбиття з клавіатури і зняття після винятку — лише позначають простір, а
звільняє його обробник `RUN`, коли повертається у свій.

Перевірка проста: `POOL FRAMES FREE` у `MEMMAP` має повертатися до того
самого числа після кожного циклу запуску й виходу.

### Планувальник

Слотів вісім. Нульовий належить ядру й готовий завжди; решта роздається
програмам. Стан кожного зберігається окремо — доти, доки «чи є
програма» було одним прапорцем, слот теж міг бути лише один.

Задача створюється побудовою підробленого кадру переривання на її
стеку: `SS`, `RSP`, `RFLAGS`, `CS`, `RIP` і поверх них п'ятнадцять
обнулених регістрів. Перемикання — два записи: зберегти `RSP`, узяти
інший.

Фонова задача рахує оберти й засинає через `hlt`. Вона існує лише щоб
довести, що перемикання справді відбувається: `BACKGROUND TURNS` у
`TASKS` має рости між двома викликами команди. При двох готових задачах
приріст становить рівно половину частоти таймера — кожна отримує кожен
другий такт.

Чого це поки не дає: **оболонка все одно вивантажується при запуску
програми**. Причина вже не в пам'яті, а в тому, що `exec` лишився
ланцюжком — той, хто викликав, зобов'язаний вийти.

## Системні виклики

Домовленість: `RAX` = номер, `RSI` = arg1, `R9` = arg2, `RDI` = arg3,
`RDX` = arg4. Виклик через `int 0x80`. Ядро зберігає всі регістри крім `RAX`.

| № | Виклик | Аргументи |
|---|---|---|
| 0 | `exit` | — |
| 1 | `get_key` | → скан-код |
| 2 | `print` | RSI=рядок, R9=колір |
| 4 | `clear_screen` | — |
| 5 | `read_file` | RSI=ім'я, R9=буфер, RDI=ліміт → байт |
| 6 | `put_char` | RSI=символ, R9=колір |
| 7 | `erase_char` | — |
| 8 | `list_files` | — |
| 9 | `blit_buffer` | RSI=`BlitArgs` |
| 10 | `get_ticks` | → такти таймера |
| 11 | `get_mouse` | → X, Y, кнопка, колесо |
| 12 | `get_time` | → години й хвилини (BCD) |
| 13 | `get_file_list` | RSI=буфер, R9=розмір |
| 14 | `write_file` | RSI=ім'я, RDI=буфер, RDX=розмір |
| 15 | `screen_info` | → (висота << 32) \| ширина |
| 16 | `open` | RSI=ім'я, R9=прапорці → fd |

### Операції над файлами

Виклики 32–35 працюють у **поточному каталозі**: ім'я зі шляхом не
розуміє ні вони, ні решта системи. Звідси наслідок, який видно просто
в меню файлового менеджера: `Copy` і `Rename` є, а `Move` (`F7` у
Windows 3.1) немає — переносити нікуди, поки ім'я не вміє нести в
собі каталог.

Нової роботи з FAT у них нема: усе це вже вміли `DeleteFileFAT32`,
`CreateDirFAT32`, `RenameFAT32` і `CopyFileFAT32`, якими користуються
команди консолі `RM`, `MKDIR` і `COPY`. Виклик лише переводить
ASCIIZ-ім'я в 11-байтний формат FAT.

Обмеження, які варто знати:

- **каталог не видаляється.** Звільнити його ланцюг легко, а ланцюги
  файлів усередині лишились би зайнятими назавжди — витік, видимий
  лише через `fat32_fsck`;
- **каталог не копіюється** — обходити дерево нічим;
- **стеля копії — 16 МБ**, розмір буфера завантаження в ядрі;
- **копія файлу в себе відхиляється.** Без цієї перевірки
  `FatWriteFile` спершу обрізав би ланцюг джерела, а потім писав би
  дані, яких уже нема.

### Правило про номери викликів

Номери **1, 5 і 9 заморожені** у тій формі, у якій їх бачать готові
бінарники на диску: порт DOOM зібрано задовго до цих змін, а його
вихідників немає.

Одного разу до них додали аргументи — ліміт у `RDI` для `read_file` і
крок рядка для `blit_buffer` — і зламали все, що вже лежало на диску:
старі програми цих полів не заповнюють, тому ядро читало як аргументи
сміття зі стеку. Так з'явилися окремі номери 24, 25 і 26.

**Ніколи не додавай аргумент до наявного номера — заводь новий.**

### Запуск програми з програми

У ядрі рівно дві задачі, тобто одночасно жива лише **одна** програма, і
всі вони вантажаться за тією самою адресою. Тому `exec` — це не «запустити
поруч», а ланцюжок: виклик лише запам'ятовує прохання, програма виходить
сама, ядро запускає названу, а коли та завершиться — повертає попередню
назад. Глибина ланцюжка — 4 рівні (`ExecStack` у ядрі).

### Файлові дескриптори

`open` читає файл **цілком** у власний буфер, `read`/`write`/`lseek`
працюють у пам'яті не чіпаючи диск, `close` одним викликом скидає буфер
назад. Свідомий компроміс: простіше й надійніше за посекторний доступ
через ланцюг кластерів.

Наслідок: **зміни втрачаються, якщо не викликати `close`**. Стеля — 8 МБ
на файл, до 8 файлів одночасно.

## Файлова система

FAT32 із повноцінним записом. Реалізовано:

- обхід **усього** ланцюга каталогу, а не першого сектора
- розширення каталогу новим кластером, коли він заповнений
- коректна робота з FAT для будь-якого номера кластера
- запис у всі копії FAT (інакше chkdsk вважає том пошкодженим)
- перезапис файлу зі звільненням старого ланцюга
- відкат при вичерпанні місця — без витоку кластерів

Алгоритм перед перенесенням в асемблер було перевірено моделлю на C
(`tools/fat32_model.c`) проти образів, зроблених стороннім кодом, і
прочитано незалежною реалізацією `pyfatfs`:

```
файли 0/1/511/512/513/4096/24424/150000/300000 байт  — біт-у-біт
перезапис 300000 → 1000 → 300000 → 512 → 0 → 65536   — без витоків
30 циклів запис/видалення по 200 КБ                  — FAT повертається у вихідний стан
300 файлів (каталог росте за межі кластера)          — 0 помилок
кластер 512 Б і 4 КБ                                 — обидві геометрії чисті
переповнення диска (70 МБ на 64 МБ)                  — fsck чистий
```

## Відомі обмеження

| Обмеження | Наслідок |
|---|---|
| Немає TCP | немає HTTP і завантаження файлів |
| Мережа на полінгу | марно палить такти, при активному трафіку можливі втрати |
| Кирилиця в редакторі не видно | шрифт ядра покриває лише ASCII 32–126: код правити можна, коментарі — читати ні |
| Імена файлів без шляхів | немає `Move`: перенести файл в інший каталог нічим |
| Файл у дескрипторі — 8 МБ | і тримається в пам'яті цілком |
| Немає підкаталогів для програм | `adapt_path` у порті fasm зрізає шлях до імені |
| Планувальник не зберігає FPU/SSE | userland мусить збиратися з `-mgeneral-regs-only` |
| Каталог не видалити й не скопіювати | вміст лишився б у FAT зайнятим, а обходити дерево нічим |
| Немає поділу на режими | усе виконується з правами ядра: NX не ввімкнено, код і дані ядра лежать в одному образі впереміш |
| `exec` лишився ланцюжком | оболонка вивантажується при запуску програми, хоча слоти й простори для співіснування вже є |
| Немає арбітражу виводу | дві живі задачі малювали б в один фреймбуфер поверх одної |
| Стек програми — 2 МБ | межу задає сторінка-вартовий на 62 МБ |
| `LoadFAT32Chain` іде по ланцюжку до кінця | ігнорує розмір із каталогу: якщо вони розійшлися, читається весь ланцюжок |
| Немає RLE у BMP | стиснені картинки не відкриються |

## Інструменти розробника

### `tools/fat32_fsck.py`

Перевіряє образ FAT32 на витоки кластерів, перехресні посилання,
розбіжність копій FAT і невідповідність розміру файлу довжині ланцюга.

```
python tools/fat32_fsck.py C:\store\1.vhd
```

Працює тільки з VHD **фіксованого** розміру: у динамічного дані розкидані
по блоках із власною таблицею.

### `tools/fat32_model.c`

Модель FAT32-шару на C зі структурою один-в-один із асемблером. Потрібна,
якщо захочеш змінити логіку роботи з кластерами: спершу перевір на моделі,
потім переноси в `kernel.asm`.

```
gcc -O1 -o model tools/fat32_model.c
```

### Налагодження мережі

`net.pcap` у корені проєкту відкривається Wireshark. Він сам перевіряє
контрольні суми й підсвічує помилки — найшвидший спосіб зловити помилку
в обчисленні суми.

### Діагностика збоїв ядра

При винятку в програмі ядро показує номер вектора і `RIP`:

```
FATAL EXCEPTION: APP KILLED TO PROTECT KERNEL
VECTOR: 000000000000000D
RIP   : 0000000004001A3C
```

| Вектор | Що це | Куди дивитись |
|---|---|---|
| `06` | `#UD` | SSE попри `-mgeneral-regs-only` |
| `0D` | `#GP` | вирівнювання стеку |
| `0E` | `#PF` | адреса поза RAM |
| `08` | `#DF` | зруйнований стек |

`RIP` мінус `0x4000000` дає зміщення у програмі — шукається через
`objdump -d userland/shell.tmp`.
