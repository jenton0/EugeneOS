## `ExitBootServices`, який не викликався

Найдовший баг проєкту. Він добре показує, чому в UEFI помилка може роками
не мати жодного симптому.

**Симптом.** На екрані налаштувань завжди світилося `RAM SIZE : UNKNOWN`,
хоча процесор і розмір диска визначалися правильно. Дрібниця, на яку
півроку ніхто не дивився.

**Гіпотеза.** `GetRamInfo` виходить по гілці `test rax, rax / jnz .done`,
тобто виклик повертає ненульовий статус. У коді стояло голе `[rax + 0x28]`,
і за припущенням це мав бути `GetMemoryMap`. Якщо припущення хибне, то за
цим зміщенням лежить сусідня функція — `AllocatePages`.

**Метод.** У копію завантажувача вбудовано зонд: обидва зміщення
викликаються з аргументами `GetMemoryMap`, а статус і `DescriptorSize`
виводяться на екран. Образ записується в копію VHD, запускається в QEMU з
`snapshot=on`, екран знімається через `screendump` монітора.

**Доказ.**

```
BS+28 ST/DS: 2/0     <- AllocatePages: статус 2, DescriptorSize не заповнений
BS+38 ST/DS: 0/48    <- GetMemoryMap:  статус 0, DescriptorSize 48
```

Статус 2 — `EFI_INVALID_PARAMETER`. 48 байтів — канонічний розмір
`EFI_MEMORY_DESCRIPTOR`. Отже, зміщення в коді були зсунуті рівно на одну
функцію.

**Наслідки.** Перший — той самий `RAM SIZE : UNKNOWN`. Другий значно
серйозніший: у циклі виходу за зміщенням `0x38` викликався `GetMemoryMap`
замість `ExitBootServices`, тобто **служби завантаження не вимикалися жодного
разу за всю історію проєкту**. Ядро стартувало поверх живої прошивки.

**Чому це не проявлялося.** Ядро одразу ставить власні GDT і IDT та
перепрограмовує контролер переривань. Прошивка лишалася формально живою, але
інертною: її обробники відключені, а сторожовому таймеру нема через що
спрацювати.

**Що це реально коштувало.** Карта пам'яті ніколи не читалася, і ядро
розкладало купу за фіксованими адресами наосліп. У QEMU не збіглося. Це рівно
той клас дефектів, що працює в емуляторі й падає на залізі.

**Виправлення.** Правильні зміщення в іменованих константах; цикл
`GetMemoryMap` + `ExitBootServices` з повтором (бо `MapKey` протухає від будь-якої
зміни карти) і стелею в 16 спроб; перевірка статусу на кожному кроці.

**Підтвердження.**

| Сценарій | Очікувано | Фактично |
|---|---|---|
| Екран налаштувань | реальний обсяг RAM | `RAM SIZE : 448 MB` |
| Завантаження ядра | консоль ОС | запрошення `C:/>` |
| `RUN GUI.BIN` | графічна оболонка | Program Manager + Console |
| `KERNEL.BIN` перейменовано | зрозуміла відмова | `EFI STATUS: 14` (`EFI_NOT_FOUND`) |

**Висновок.** У UEFI немає захисту від такої помилки: невірне зміщення дає
валідний покажчик на іншу функцію, вона повертає код помилки, а його ніхто
не перевіряє. Тому виправлення — це не лише правильні числа, а й іменовані
константи та обов'язкова перевірка статусу, щоб наступного разу дефект
кричав, а не мовчав.

## Відеорежими й порядок каналів

**Що показав перелік у QEMU.** 30 режимів від 640×480 до 2560×1600. У всіх
крок рядка дорівнює ширині, і у всіх формат пікселя 1 (BGRA). Це
підтверджує два припущення, на яких мовчки трималося малювання, і пояснює,
чому помилка з кроком рядка не могла тут проявитися: QEMU ніколи не вирівнює
рядки.

```
[ 0 ] 1280X800   STRIDE 1280  FMT 1  <-- ACTIVE
[ 1 ] 640X480    STRIDE 640   FMT 1
[ 2 ] 800X480    STRIDE 800   FMT 1
...
[ 29 ] 2560X1600 STRIDE 2560  FMT 1
```

**Як перевірено RGB, якщо QEMU дає лише BGR.** Формат примусово виставили
в 0 у копії завантажувача й подивилися, що вийшло:

| Задумано `0x00RRGGBB` | Норма (BGR) | Примусовий RGB |
|---|---|---|
| `0x0000AA` фон | синій | `#AA0000` червоний |
| `0xFFFF00` жовтий | жовтий | `#00FFFF` блакитний |
| `0xFF0000` червоний | червоний | `#0000FF` синій |
| `0x00FF00` зелений | зелений | `#00FF00` без змін |
| `0xFFFFFF`, `0xAAAAAA`, `0x555555` | сірі | без змін |

Червоний і синій міняються місцями, зелений і сіра шкала лишаються — тобто
перестановка відбувається рівно там, де має.

## Заміри завантажувача

Пункт меню `[ 3 ] RUN BENCHMARKS`. Годинник — `RDTSC`, єдиний доступний і до,
і після `ExitBootServices`. Калібрується один раз об `Stall()` на 100 мс.
Кожен вимір повторюється й усереднюється.

**Стенд:** QEMU 10.2, TCG, OVMF, 1280×800, ядро 78 712 Б.

| Що | Час |
|---|---|
| Калібрування | 2689 тактів на мікросекунду |
| `LocateProtocol` + читання режиму | 107 мкс |
| Перелік 30 режимів (`QueryMode` × 30) | 203 мкс |
| Дані про процесор, пам'ять і диск | 306 мкс |
| Відмальовка екрана налаштувань | 1889 мкс |
| **Разом до першого екрана** | **2508 мкс** |
| Заливка екрана, прямий запис | 1630 мкс |
| Заливка екрана, `Blt` `EfiBltVideoFill` | 1376 мкс |
| `Open` + `GetInfo` + `Read` ядра | 7773 мкс |

**Що з цього випливає.**

- *Робота з GOP майже безкоштовна:* ~7 мкс на `QueryMode`, разом 12 % часу
  до першого екрана. Перелічувати режими на кожному завантаженні виправдано.
- *Головна витрата — малювання:* 75 % старту, з них 1630 мкс — сама заливка
  фону, ~260 мкс — увесь текст.
- *Читання ядра дорожче за все інше разом:* ~10 МБ/с через `SimpleFileSystem`.
  Від старту до передачі керування ядру — близько 10 мс.

**Прямий запис проти `Blt`.** `Blt` вийшов на 16 % швидшим, але цьому числу
вірити не можна. Під TCG фреймбуфер — звичайна пам'ять емулятора, тож
порівнюються два згенеровані цикли, а не два шляхи до відеопам'яті. Цей вимір
показує, що **питання неможливо закрити на емуляторі**.

**Чого цим стендом не виміряти:** прямий запис проти `Blt`; крок рядка ≠
ширині; формат, відмінний від BGR; таблиці режимів інших прошивок.

**Порівняння з іншими завантажувачами** — не за швидкістю, а за тим, як
фреймбуфер потрапляє до ядра:

| Завантажувач | Що робить із графікою |
|---|---|
| `systemd-boot` | графіки не торкається, передає керування EFI-заглушці |
| GRUB2 | власна відеопідсистема, GOP — один із драйверів; фреймбуфер іде тегом Multiboot2 |
| Limine | сам ставить режим і віддає опис у структурі свого протоколу |
| EugeneOS | сам ставить режим через `SetMode` і віддає базу, ширину, висоту й крок у регістрах |

## Завантаження ядра: як було

Раніше не перевірявся жоден статус: розмір просили «мегабайт і сподіваємось»,
адреса `0x100000` бралася на віру без резервування, а відсутній `kernel.bin`
призводив до стрибка на те, що випадково лежало за цією адресою. Замість
`jmp $` на чорному екрані тепер — екран із причиною та кодом.

## Редактор: від друкарської машинки до редактора

Буфер редактора був статичним масивом на 32 КБ у тілі ядра, а більший файл
**мовчки обрізався**: `kernel.asm` (понад 280 КБ) відкривався на 11 %, і
збереження знищувало решту. Довжина шукалась за нульовим байтом, тож нуль
усередині файлу теж обрізав його.

Гірше: `EditorCursor` був одночасно позицією запису й кінцем тексту. Символи
дописувались лише в кінець, `Backspace` стирав лише останній, а стрілки
рухали **екран**, а не каретку. Це був не редактор, а друкарська машинка з
прокруткою.

Тепер довжина (`EdLen`) і каретка роздільні, вставка й видалення працюють
будь-де, буфер на 4 МБ винесено в окрему ділянку `0x7100000` — і ядро від
цього схудло на 32 КБ.

Коли файл почав вантажитися повністю, знадобився захист: без режиму
`BINARY FILE - READ ONLY` команда `EDIT KERNEL.BIN` відкрила б ядро на
редагування, де один символ і `F2` зіпсували б його остаточно.

`F3` (перехід на рядок) з'явився тому, що FASM повідомляє про помилку
номером рядка.

## Чому перебудували графічну оболонку

Спершу віконних інтерфейсів було два, написані з різницею в три місяці:

- `libgui/gui.c` — новий шар із частковим оновленням екрана, пропорційним
  шрифтом і чергою подій. Ним користувалася лише демка;
- `userland/shell.c` — справжня оболонка з власним шрифтом на 64 гліфи
  (лише великі літери), власним буфером кадру й повним виведенням екрана
  щокадру.

Поведінка вікна в оболонці була гілкою `if/else` **всередині циклу рендеру**:

```c
if (w->app_type == APP_CONSOLE)       { ...малюємо консоль... }
else if (w->app_type == APP_EDITOR)   { ...малюємо редактор... }
else if (w->app_type == APP_EXPLORER) { ...малюємо провідник... }
```

Кожен новий додаток означав правку рендерера, а часткове оновлення оболонці
не діставалося. Обидва шари злили в один, з поділом як у Windows 3.1.

## Програма у вікні: куди подівся час

Перший робочий запуск DOOM у вікні дав кадрів десять. Час забирали три
речі, і жодна з них не була самою грою.

**Дві задачі з трьох нічого не робили.** Планувальник ділить час між
*готовими* задачами, а готових було три: ядро опитувало прапорці в циклі,
оболонка крутила `wm_pump()` без подій. Грі діставалася третина. Тепер ядро
робить `hlt`, а оболонка кличе `syscall 45`, коли за оберт нічого не сталося.

**Під вікном малювалося те, чого не видно.** `paint_pass` малював стіл і всі
вікна знизу вгору на весь брудний прямокутник — двадцять разів на секунду.
Тепер усе під найвищим вікном, яке накриває прямокутник цілком, пропускається.

**Ділення на кожен піксель.** `gui_bitmap_fit` ділив на кожен піксель. Для
значків 32×30 це було непомітно, а на полотні розміром з екран — сотні тисяч
ділень на кадр. Тепер стовпчики рахуються раз на виклик.

Ще три пастки:

- **Полотно 640×400** — і гра малювала зі зсувом: DOOM центрує кадр під
  розмір «екрана», і все, що не влізло, зрізалось. Тепер полотно з екран.
- **Полотно з купи оболонки** — і вікно лишалося чорним: `PagingCloneSpace`
  робить купу приватною, тож дитина малювала у свою копію. Тепер полотно видає
  ядро у спільній частині простору.
- **Вікно закривалося, поки гра вантажилась**: оболонка питала «чи жива
  дитина» в щілину між проханням про запуск і появою задачі. Звідси `SpawnBusy`.

## Текст програми у вікні

Текстові виклики малюють прямо у фреймбуфер, повз blit. Спершу вони працювали
як раніше — і журнал запуску DOOM ліг поверх усієї оболонки. Тоді їх
заборонили для задач із полотном — і текст просто зникав: програма, що лише
друкує, у вікні не показувала нічого. Діалогу запуску довелося б питати «у
вікно чи на весь екран», тобто вимагати від користувача знати, малює програма
графікою чи друкує.

Рішення — буфер тексту й одне правило: показувати текст, доки не
намальовано жодного кадру. Питання в діалозі зникло само.

Вікно спершу закривалося разом із програмою — і `HELLO`, що друкує й
виходить за мілісекунди, зникав раніше, ніж устигав намалюватися. Тепер
вікно з результатом закривається руками.

## TCP: як шукали помилки

Три різні речі виглядали однаково — «не вдалося з'єднатися».

1. `ParseIp` зберігає й **відновлює** RSI, тому порт розбирався з початку
   рядка: замість `80` виходило `10`.
2. Одне повідомлення на всі випадки нічого не пояснювало. Причини розділено
   на п'ять, і найважливіша — `RST`: пакет **дійшов**, протокол працює,
   закритий лише порт.
3. Лічильник прийнятих сегментів показав, що `10.0.2.2:80` мовчить не через
   нашу помилку — на хості ніхто не слухає, а брандмауер відкидає мовчки.
   Перевірка на `1.1.1.1` пройшла з першого разу.

Перша версія `GET` не слала `Host:` — і Cloudflare відповідав `403` з кодом
`1003` («за голою адресою не пускаємо»). З заголовком та сама команда дістає
`200 OK`.

## Самокомпіляція: протокол перевірки

Знято на копії диска в QEMU:

| Крок | Результат |
|---|---|
| `EDIT KERNEL.ASM` на джерелі 302 746 Б | відкрився повністю, `SIZE 302746` у заголовку |
| `F3` → рядок 4745 | `LINE 4745 COL 1` |
| 39 × `→`, `Delete`, ввід `3` | `Version 2.0` → `Version 3.0` **у середині файлу** |
| `F2` | збережено, розмір не змінився |
| `RUN FASM.BIN KERNEL.ASM K.BIN` | `4 passes, 47960 bytes` |
| `INSTALL K.BIN` | `INSTALLED. PREVIOUS KERNEL SAVED AS KERNEL.BAK` |
| `REBOOT` | система стартувала з написом `EUGENE OS  Version 3.0` |
| `KERNEL.BAK` проти еталона | побайтово збігається з попереднім ядром |

Те саме джерело, зібране всередині ОС і віндовим fasm, дає побайтово
однакові файли (`cmp` мовчить на 78 712 байтах).

Відома дірка: резервна копія рятує лише доти, доки система завантажується.
Пункт завантажувача для вибору `KERNEL.BAK` закрив би її.

## FAT32: перевірка моделлю

Алгоритм перед перенесенням в асемблер перевіряли моделлю на C
(`fat32_model.c`, структура один в один з асемблером) проти образів,
зроблених стороннім кодом, і читали незалежною реалізацією `pyfatfs`.
Образи перевіряв `fat32_fsck.py` (витоки кластерів, перехресні посилання,
розбіжність копій FAT, розмір проти довжини ланцюга; лише VHD фіксованого
розміру).

```
файли 0/1/511/512/513/4096/24424/150000/300000 байт  — біт-у-біт
перезапис 300000 → 1000 → 300000 → 512 → 0 → 65536   — без витоків
30 циклів запис/видалення по 200 КБ                  — FAT повертається у вихідний стан
300 файлів (каталог росте за межі кластера)          — 0 помилок
кластер 512 Б і 4 КБ                                 — обидві геометрії чисті
переповнення диска (70 МБ на 64 МБ)                  — fsck чистий
```

> Обидва інструменти в репозиторій поки не додані.
